# Provider durability

Core owns discovery and recovery; product agents cannot publish recovery policy
or runtime attestations. Agent grants and independent QA remain immutable.

The CLI resolver tries the managed install, explicit configuration and standard
vendor locations. A broken installation cannot mask a responsive fallback.
An adapter keeps one executable identity through detection, authentication and
execution. Replaced launch files are rejected. Version families qualify for a
bounded isolated protocol test; version strings alone never prove capabilities.
Codex's isolated tool image remains pinned separately from its host CLI.

The independently reviewed recovery policy captures the existing grant and
approved capabilities once. The monitor can renew those capabilities against
canonical successful tests, measured usage and matching runtime identities. It
records runtime attestations, not fabricated independent QA. No paid API fallback,
login, installer, model download, permission expansion or product merge occurs.

Normal dispatch requires matching installation evidence. Recovery runs two small
read checks after identity changes and checks changing defaults at most daily.
Previously approved writers also stage a fixed disposable compatibility artifact;
engineering checks run inside the existing isolated boundary. Nothing is merged.
Failed recovery uses a 30-minute cooldown and records one alert per changed
failure. Existing control limits, pause/kill, authentication and quota still apply.
Revoked policy, role or capability approval blocks renewal.

Ollama startup uses the same executable discovery module. An explicit moved binary
can be configured with `TRIAD_OLLAMA_EXECUTABLE` in the host environment or `.env`;
the equivalent names are `TRIAD_CODEX_EXECUTABLE`, `TRIAD_CLAUDE_EXECUTABLE` and
`TRIAD_GROK_EXECUTABLE`. Existing `OLLAMA_MODELS` is retained. The supervisor does
not copy model data or download replacements.

Daily product cycles evaluate inspection, local synthesis, selection, UI build,
independent QA and debrief assignments before the first product inference. The
recorded readiness report explains each blocked stage. Dispatch still rechecks
authority and readiness because conditions can change during a cycle.

The host rollout command `tools/provider_recovery.py --activate --implementation
<reviewed implementation ID> --commit <reviewed commit>` activates the reviewed
policy. `--reconcile` requests recovery immediately; otherwise the existing
five-minute monitor handles it. Without arguments, the command prints status.
Diagnostics and provider cards show recovery state in readable text.

Unsupported protocol families and incompatible boundary behavior remain blocked
with an actionable reason. This recovery mechanism does not promise compatibility
with arbitrary future vendor APIs.
